# CONSULTATION STREAM & DEDUPLICATION PROTOCOL

## 1. Typed Stream Event Protocol

```typescript
export type ConsultationStreamPhase =
  | 'STARTED'
  | 'UNDERSTANDING'
  | 'ASTROLOGY_ANALYSIS'
  | 'GENERATING'
  | 'STREAMING'
  | 'COMPLETED'
  | 'FAILED';

export type ConsultationEvent =
  | {
      type: 'CONSULTATION_STARTED';
      conversationId: string;
      messageId: string;
      requestId: string;
    }
  | {
      type: 'PHASE_CHANGE';
      conversationId: string;
      messageId: string;
      phase: ConsultationStreamPhase;
      description?: string;
    }
  | {
      type: 'TEXT_DELTA';
      conversationId: string;
      messageId: string;
      delta: string;
    }
  | {
      type: 'COMPLETED';
      conversationId: string;
      messageId: string;
      message: ChatMessage;
    }
  | {
      type: 'FAILED';
      conversationId: string;
      messageId: string;
      errorCode: string;
      errorMessage: string;
    };
```

---

## 2. Deduplication & Idempotency Rules

1. **Request Identity**:
   - `clientMessageId`: Generated by the mobile client before calling the mutation.
   - `requestId`: Unique UUID for backend generation tracing.
2. **Database Integrity**:
   - Compound index on `{ conversationId: 1, clientMessageId: 1 }`.
   - If an existing user message with the same `(conversationId, clientMessageId)` is found, `sendMessage` immediately returns the existing document without creating duplicate assistant tasks or debiting credits.
3. **Billing Invariant**:
   - Exactly one debit per successful completed consultation response.
   - Retries on failed messages reset the failed document in place without additional billing.
